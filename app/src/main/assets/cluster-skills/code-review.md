# 代码评审

## 只报真问题

**一条真问题的判据**：能说清**什么输入/什么时序/什么并发下会出错**。
说不清触发条件的一律丢掉，即使它「看起来不太好」。

| 丢 | 留 |
|---|---|
| 「这里可以写得更好」 | 「用户输入为空时这行会 NPE」 |
| 「命名不统一」 | 「这个函数名和它做的事相反，调用方会误用」 |
| 「建议加个注释」 | 「这段的锁在 return 前没释放，异常路径会死锁」 |

## 每条问题必须带五要素

1. **位置**：文件 + 行号
2. **触发条件**：什么情况下会出问题（输入值 / 并发时序 / 平台差异）
3. **后果**：崩了？数据错了？死锁？只是难看？
4. **证据**：为什么会这样（引用被调用的代码/文档/实测输出）
5. **修法**：具体怎么改

**没有第 2 条的意见不算问题**，最多算吹毛求疵，且必须标出来。

## 禁止的评审行为

- ❌ **不做无证据的安全指控**。「这里可能有注入风险」而不指出哪个输入不可信 = 无效指控。
- ❌ **不评审用户没要求改的东西**。风格、命名偏好、注释多少，除非违反项目已有约定。
- ❌ **不把「我习惯这么写」当依据**。项目约定 > 个人偏好。
- ❌ **不刷数量**。3 条真问题胜过 20 条凑数的。
- ❌ **不改完代码就说「建议改为」**——给出可直接用的替换片段。

## 高危清单（优先扫这几类）

| 类别 | 找什么 |
|---|---|
| 资源 | 文件流/连接/锁没关；异常路径漏释放 |
| 空值 | `!` 强制解包、平台类型强转、`0` 与 `null` 混淆 |
| 并发 | 共享可变状态、check-then-act、双重初始化 |
| 边界 | 下标越界、长度假设、单位混用、整数溢出 |
| 错误处理 | 吞异常（空 catch）、错误包装丢失原因、失败后状态未回滚 |
| 安全 | 真实可注入点（用户输入 → SQL/命令/路径拼接）、硬编码密钥 |

## 工作流

1. 先读该模块的**已有测试**，测试即规格。
2. 对照验收标准 / 接口契约看，不凭个人偏好。
3. 按高危清单扫一遍。
4. 每条过「触发条件」筛，筛不掉的直接删。
5. 问题在前，按严重度排序。
6. 结尾给一句整体判断（能不能合）。

## 自检清单

- [ ] 每条问题都有**触发条件**
- [ ] 每条带齐五要素（位置/触发/后果/证据/修法）
- [ ] 无证据的安全指控已删除
- [ ] 未把个人风格偏好当问题
- [ ] 高危清单 6 类已扫过
- [ ] 已读该模块的现有测试并对照
- [ ] 问题按严重度排序，问题在前
- [ ] 每条给出了可直接用的修法
- [ ] 给了「能不能合」的明确结论

## 交付时说清

几条阻断级、几条必修、有没有证据不足的地方。
**「没有发现问题」要写成「在所扫范围内未发现阻断/必修问题，扫了哪几类」**，
不能只写「看起来没问题」。
