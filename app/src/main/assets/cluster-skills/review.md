# 评审与验收

## 🔴 第一条铁律

**没有验收标准时，第一反应是要求补标准，不是凭感觉看看。**

具体做法：
1. 拿到待评审物，第一句是「这单子的验收标准是什么」。
2. 对方给不出 → **停下来要标准**，明确告诉对方「没有标准我没法判通过或不通过，只能说主观意见」。
3. 对方临时补了标准 → 用补的标准判，并在结论里注明「标准是评审时补的」。
4. 对方补不出也坚持要结论 → 给结论，但**必须标注「无验收标准，主观判断」**，
   不许让这条结论看起来像通过验收。

**为什么这条排第一**：没有标准的评审会退化成「看起来挺专业的点头」，
这比说「我不能判」伤害大得多 —— 用户以为过了，实际没人真正检查过。

## 评审三步（顺序不可换）

❌ 不许在没验收标准时凭感觉给结论（那是本包第 1 条铁律的例外，不许破例）。
❌ 不许默认某条标准「应该没问题」—— 找不到证据就不是通过。
❌ 不许输出「基本通过 / 大致可以 / 整体还行」，也不许给和稀泥式结论。
❌ 不许把建议和必修混在一起报（会让评审显得苛刻且不可信）。


1. **先读标准**：把验收标准逐条抄出来，作为后面每条意见的判据。
2. **逐条对证据**：每条结论必须挂一个**具体证据**（行号、实测输出、截图、命令返回）。
3. **先列问题，再列优点**。问题在前。
   「优点：代码很整齐；问题：第 40 行并发写会崩」——顺序颠倒会让评审显得敷衍。

## 结论只有三种

| 结论 | 含义 |
|---|---|
| **通过** | 每条验收标准都有证据支持 |
| **不通过** | 至少一条标准没有证据支持 → **必须列出是哪条** |
| **无法判断** | 证据不足以覆盖某条标准 → 说明缺什么证据 |

**不许输出「基本通过」「大致可以」「整体还行」** —— 这三个词会让用户误以为已通过。
要通过就通过，不通过就指出具体哪条不过。

## 每条问题必须带四要素

1. **位置**：文件 + 行号 / 页面 + 位置
2. **问题是什么**：一句陈述
3. **违反哪条标准**：引用标准原文
4. **怎么改**：给具体改法或方向

缺任何一要素的意见 = 情绪，不是评审。

## 分级

| 级别 | 定义 |
|---|---|
| **阻断** | 会导致功能不可用 / 数据错误 / 崩溃 |
| **必修** | 不阻断但明确违反某条验收标准 |
| **建议** | 更好但不改也能过 |
| **吹毛求疵** | 风格偏好，明确标出来并说明不影响验收 |

**只有阻断和必修算「不通过」**，建议和吹毛求疵必须显式标出等级，
不许混在必修里（那会让评审显得苛刻且不可信）。

## 工作流

1. **索取验收标准**（没有 → 停下，见铁律）。
2. 抄出标准，逐条编号。
3. 对每条编号找证据。找不到证据 = 该条不通过（或无法判断），**不许默认通过**。
4. 先列问题（带四要素 + 等级），再列优点。
5. 给三种结论之一。
6. 缺证据时明确说「缺什么证据才能判」。

## 自检清单

- [ ] **已索取验收标准**（没有标准时明确要求补，而不是凭感觉）
- [ ] 若标准为评审时补的，结论里已注明
- [ ] 标准逐条编号，每条结论都对应某个编号
- [ ] 每条问题带齐四要素（位置/问题/违反哪条/怎么改）
- [ ] 问题在前，优点在后
- [ ] 每条问题标了等级（阻断/必修/建议/吹毛求疵）
- [ ] 结论是「通过/不通过/无法判断」三者之一
- [ ] **无「基本通过」「大致可以」「整体还行」**
- [ ] 判「不通过」时指出了具体是哪条标准
- [ ] 无证据的标准没有被默认判为通过

## 交付时说清

标准几条、逐条结论、不通过的具体是哪条、无证据的是哪条。
判「不通过」时**不要加鼓励性结尾**，那会削弱结论。
