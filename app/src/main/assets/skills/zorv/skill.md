# 视频号账号诊断与拆解（付费版）【零一数科·出品】

> 版本：v0.1.0 · 作者：小风、CoderPig、Awen

使用远端服务拆解微信视频号账号。输入为视频号**账号名称**（昵称）。脚本 [scripts/analyze_account.py](scripts/analyze_account.py) 负责全部 HTTP 调用（发起任务 + 轮询 + 交付报告），接口说明见 [references/api.md](references/api.md)。

## 执行流程

按以下顺序执行，每一步都对应后续章节的细节：

1. **取 API Key**：读技能目录下 `config.json` 的 `LY_API_KEY`（回退环境变量）。缺失或不合法时，按「鉴权」流程引导用户获取并写入，再继续。
2. **识别输入**：判断用户是否提供了视频号账号名称。无效或缺失时，按「引导话术」对应场景引导用户更正。
3. **账号名称准确性提醒 + 预估扣点 + 二次确认（必做关卡）**：首次执行（非 `--task-id` 恢复）时，先用 `--estimate-only` 创建任务拿到 **task_id 和预计扣点**（服务端返回就用真实值，否则约 168 点），「确认要开始吗」让用户明确确认；未确认不要轮询、不要继续。**预估约 168 点只是参考，最终扣点按任务复杂度而定、以服务端实际计费为准（可高可低）。**恢复超时任务不重复扣点，跳过本步。详见「账号名称准确性」「扣点与确认」。
4. **发起拆解**：用账号名称调发起接口取得 `task_id`（`--estimate-only` 已完成创建）。
5. **轮询等待 + 持续反馈进度**：用 `--task-id` 轮询，**每轮把 stderr 的进度行转述给用户**（状态/已等待时长/当前阶段/进度文案或百分比；服务端没返回进度细节时会每 30s 保活一行「服务端处理中，请稍候…」），让用户全程知道在推进，不要沉默。通常几分钟出报告。
6. **交付报告**：终态完成后，把分隔符之间的 Markdown 渲染给用户，告知本次实际扣点与报告查看方式。

> 若是恢复已超时的任务，跳过 1 之后的鉴权检查后直接用 `--task-id <id>` 从第 5 步恢复轮询。

任一步异常按「退出码处理」表对号入座，**不要自行判定失败**。

## 鉴权

Token 取「技能目录」（SKILL.md 所在目录）下 `config.json` 里的 `LY_API_KEY` 字段，回退到环境变量 `LY_API_KEY`。脚本请求头使用 `Authorization: Bearer <api_key>`。`config.json` 形如：

```json
{ "LY_API_KEY": "你的密钥" }
```

运行脚本前，先按下面的流程确认 key 就绪。**任何时候都不要编造或猜测 key。**

1. **检查是否已有 key。** 读技能目录下的 `config.json`，看 `LY_API_KEY` 是否为非空字符串；若没有，再看环境变量 `LY_API_KEY`。两者任一有值即视为就绪，直接进入后续流程。
2. **缺失则引导用户获取。** 若都没有，停下来提示用户前往 <https://claw.lingyishuke.com/webapps/01claw-auth/index.html?source=workbuddy> 获取 API Key，并让用户把拿到的 Key 直接发给你。在拿到 key 之前不要运行脚本。
3. **记录用户发来的 key。** 收到 key 后，把它写入技能目录下的 `config.json` 的 `LY_API_KEY` 字段（保留文件其它内容），然后再运行脚本。该文件已被 `.gitignore` 忽略，不会入库。
4. **鉴权失败（退出码 3）时。** 多半是 key 失效或过期。提示用户重新前往上述地址获取新 key，按第 3 步覆盖写入 `config.json` 后重试；不要反复用同一个失效 key 重跑。

> 若运行报 SSL 证书错误（`CERTIFICATE_VERIFY_FAILED` 等，常见于 macOS 缺证书或企业代理环境），可设环境变量 `LY_SKIP_SSL_VERIFY=1` 后重试。注意：跳过证书校验有中间人风险，仅在受控环境临时使用。

## 输入识别

单次只处理一个账号名称：

- **视频号账号名称（昵称）**：任意非空字符串，如「央视新闻」「papi酱」。直接把名称传给脚本。
- 可选附带 `--platform` 指定平台，不传也行。

若用户未提供账号名称、或只给了链接/视频文件而本技能无法直接处理，按「引导话术」对应场景引导。若一次给出多个名称，先让用户指定一个。

## 账号名称准确性

本技能是按**账号名称**去定位并拆解对应账号的，名称错了就会拆到别的账号或拆不出来，因此运行前必须确认账号名称准确无误：

- 拿到用户给的账号名称后，先简短复述一遍确认：「我将拆解账号【<名称>】的……，对吗？」；用户给的名称含错别字、歧义或为简称时，主动向用户核对完整、正确的账号昵称。
- 建议用户从微信视频号里复制该账号的准确昵称后再发给你，避免手打出错。
- 确认无误后再进入「扣点与确认」。

## 扣点与确认

本技能每次「新发起」拆解任务都会扣点，且账号拆解任务重、链路长，**单次消耗的点数非常大**，是一笔不小的成本。整条链路对用户的扣点感知由你（assistant）来贯穿，**务必在开始轮询/生成报告前让用户确认**：

- **拿到真实预估扣点**：识别成有效账号名称、确认名称无误、API Key 就绪后，先运行一次 **`--estimate-only`** 创建任务。脚本会打出三行标记（无网络/余额问题时）：

  ```text
  ACCOUNT_TASK_ID=<task_id>
  ACCOUNT_ESTIMATE_POINTS=<预计扣点>
  ACCOUNT_ESTIMATE_SOURCE=<服务端返回 | 默认估算（服务端未在创建响应里返回点数字段）>
  ```

  `ACCOUNT_ESTIMATE_POINTS` 就是本次预计扣点：服务端在创建响应里返回了点数字段就用真实值，没返回就回退约 168 点（来源见 `ACCOUNT_ESTIMATE_SOURCE`）。**这只是预估参考，实际扣点按任务复杂度而定，最终以服务端实际计费 / 01Claw 账户扣减为准（可高可低）。**记下 task_id，等用户确认后用它轮询。注意：`--estimate-only` 已经在服务端创建了任务，**确认通过后用 `--task-id <task_id>` 继续轮询即可，不要重新 `--estimate-only` 或重新创建**。

- **执行前确认（仅新任务，非 `--task_id` 恢复）**：拿到上面三行后，**继续轮询之前**向用户发出确认，**等用户明确同意后才能用 `--task-id` 轮询**。确认话术如下，把 {预计扣点} 换成 `ACCOUNT_ESTIMATE_POINTS` 的值：

  > ⚠️ 即将开始拆解账号【\<名称>】，提醒你两件事：
  >
  > 1. **本次任务消耗的点数非常大**——预计约 {预计扣点} 点（实际以服务端扣点为准，可能因任务复杂程度上浮），**任务已创建、确认后即继续扣点**，请确认你知晓这笔成本。
  > 2. **账号名称务必准确无误**——拆解是按账号名称定位的，错一个字就可能拆到别的账号或拆解失败，白扣点。建议从微信视频号里把账号准确昵称复制过来核对。
  >
  > 确认要开始拆解吗？回复「确认/继续」我就继续；如果还要改账号名或暂不拆解，告诉我即可。

  等用户明确确认（如「确认」「继续」「开始吧」）后再用 `--task-id` 轮询；用户未确认、未回应、含糊或要求改主意时，**不要再轮询**。不要因为用户「可能想拆」就默认继续。

- **执行成功后回告实际扣点**：见「输出交付」，把脚本透出的 `ACCOUNT_POINTS_USED` 作为实际扣点告诉用户，并给出查看报告的方式。

- **执行失败后告知点数返还**：见「退出码处理」，任务已发起但未成功产出报告时，告知用户「因网络原因本次任务执行失败，相应点数已返还」并询问是否重试。

> 恢复已有任务（`--task_id`）时点数已在发起时扣除，本次仅继续轮询，不重复扣点、不需再次确认。

## 运行方式

在 skill 目录下运行。

**第一步：创建任务 + 拿到预计扣点（不轮询，用于确认前报价）：**

```bash
python3 scripts/analyze_account.py "<账号名称>" --estimate-only
```

可选附带平台：

```bash
python3 scripts/analyze_account.py "<账号名称>" --platform "<平台>" --estimate-only
```

**第二步：用户确认后，用 task_id 轮询出报告：**

```bash
python3 scripts/analyze_account.py --task-id "<task_id>"
```

恢复超时的任务同上（跳过创建，直接轮询）。

可选参数：

- `--estimate-only`：只创建任务、拿 `task_id` 与预计扣点后即退出（不轮询）。打三行标记：`ACCOUNT_TASK_ID` / `ACCOUNT_ESTIMATE_POINTS` / `ACCOUNT_ESTIMATE_SOURCE`。用于让助手在确认前先把预计扣点告诉用户。
- `--platform <平台>`：平台，可不传。
- `--task-id ID`：已有的任务 ID（来自 `--estimate-only` 的 `ACCOUNT_TASK_ID`，或超时恢复），直接进入轮询。
- `--out PATH`：报告输出路径，目录或文件均可。
- `--max-wait`：等待上限秒，默认 600。
- `--interval`：轮询间隔秒，默认 8（文档建议 5～15s）。

## 发起拆解与轮询

脚本向 `POST /api/v1/common-gateway/analysis-skill/wx-video-account-analysis` 发起任务，body 必填 `account_name`，可选 `platform`。成功后取得 `data.task_id`，再轮询：

```text
GET /api/v1/common-gateway/analysis-skill/wx-video-account-analysis/{task_id}
```

进度写到 stderr，报告写到 stdout。**轮询期间每收到一行 stderr 进度就简短转述给用户**——脚本会在状态/阶段/进度文案/百分比变化时打一行，没变化时每 30s 打一行保活（更新已等待时长）。典型 stderr 行形如：

```text
[执行中] · 已等待45s · 当前阶段：视频拆解
[执行中] · 已等待120s · 服务端处理中，请稍候…
[完成] · 已等待210s
```

转述时用人话，不要原样贴 `[执行中] · 已等待Ns` 这种技术日志，例如「正在拆解视频，已等约 2 分钟，稍等…」。状态枚举见 [references/api.md](references/api.md)。

> 注意：真实接口在 `pending`/`running` 阶段**通常不返回** `current_stage` / `progress_message` / 进度百分比字段（样例里这些只在完成态的 `steps_timing` 出现过）。所以脚本会回退用「状态 + 已等待时长」反馈，并在没细节时每 30s 保活一行「服务端处理中，请稍候…」——这是**正常的**，不代表卡住。只要 status 在推进或保持 running 即可。耐心等 status 变为 `completed`。

远端拆解通常需要几分钟（账号拆解任务较复杂，可能 5–10 分钟甚至更久）。**轮询一开始就告诉用户**「已开始拆解、预计需要几分钟，我会随时同步进度」，之后边轮询边把最新的进度行转述给用户，**全程不要长时间沉默**。脚本运行期间不需要做其他操作，等待脚本返回即可。

若发起任务时余额不足，脚本以退出码 4 退出。引导用户前往 <https://claw.lingyishuke.com/webapps/01claw-auth/index.html?source=workbuddy> 充值；充值前不要继续轮询。

## 输出交付

成功时 stdout 形如：

```text
ACCOUNT_POINTS_USED=<本次实际扣点，可能为空>
ACCOUNT_REPORT_FILE=<报告文件绝对路径>
=== ACCOUNT_REPORT_START ===
<完整 Markdown 报告>
=== ACCOUNT_REPORT_END ===
```

交付时按顺序做三件事：

1. **渲染报告（务必渲染全文）**：截取 `=== ACCOUNT_REPORT_START ===` 与 `=== ACCOUNT_REPORT_END ===` 之间的 Markdown，**原样作为 Markdown 渲染到对话中**——不要包成代码块、不要只给文件路径、不要用摘要替代全文。报告可能较长，也要完整渲染，让用户能直接看到排版好的账号拆解报告。分隔符之间即为可直接渲染的内容，无需再处理。
2. **告知实际扣点**：若 `ACCOUNT_POINTS_USED` 非空，告诉用户「本次任务实际扣除 {点数} 点」；为空时回退用第一步 `--estimate-only` 给的 `ACCOUNT_ESTIMATE_POINTS` 值，说「本次任务约扣 {预估} 点（实际以服务端扣点为准，可在 01Claw 账户查看）」。两步报的数字保持一致。
3. **告知报告查看方式**：报告已渲染在上方对话中；同时已保存为 Markdown 文件，路径见 `ACCOUNT_REPORT_FILE`，可直接打开该文件查看或归档。

> **报告是怎么来的**：接口实际返回的是**结构化 JSON**（`data.result.sections[]` 或 `data.report_v2`），**并非**现成的 `data.markdown`。脚本会把结构化结果渲染成 Markdown 报告（按 section/block 出标题、列表、表格）放到分隔符之间；若服务端某次直接返回了现成 `markdown` 字段，脚本会优先用它。因此分隔符之间一定是渲染好的、可直接渲染的 Markdown，助手只管原样渲染全文即可。详见 [references/api.md](references/api.md)。

若文件写入失败但 stdout 有报告正文，仍按上面方式在对话中交付报告并说明扣点。

## 退出码处理

| 码 | 含义 | 处理 |
| --- | --- | --- |
| 0 | 成功 | 按「输出交付」处理。 |
| 2 | 输入错误 | 让用户提供视频号账号名称；任务未发起，**不扣点**。 |
| 3 | 缺 key 或鉴权失败 | 按「鉴权」流程处理：引导用户前往 `https://claw.lingyishuke.com/webapps/01claw-auth/index.html?source=workbuddy` 获取 key，收到后写入 `config.json` 再重试。任务未发起，**不扣点**。 |
| 4 | 发起拆解失败，含余额不足 | 展示服务端 message；余额不足时引导用户前往 `https://claw.lingyishuke.com/webapps/01claw-auth/index.html?source=workbuddy` 充值，有服务端充值链接则优先用它。任务未成功发起，**不扣点**。 |
| 5 | 任务失败 | 告知用户「因网络原因本次任务执行失败，相应点数已返还」；转述 stderr 中的失败原因，并询问是否重试一次。 |
| 6 | 发起拆解或轮询阶段的网络 / 限流 / 任务失效 | 停止并告知用户「因网络原因本次任务执行失败，相应点数已返还」；说明网络、限流、服务端不可用或任务失效等实际原因；附 stderr 中具体信息，询问是否重试。 |
| 7 | 完成但无可渲染报告 | status 已 completed，但响应里既无 `markdown`、也无 `result.sections` / `report_v2` 可渲染（脚本已内置 60s 宽限轮询，多数能补齐）。仍为空时：转述 stderr 中的 `status`/`error_message`（若有）；建议稍候用 `--task-id <id>` 重新轮询一次；多次仍空则联系服务端排查。任务已发起，按实际扣点处理。 |
| 124 | 超时 | 说明任务可能仍在进行，附 task_id，用 `--task-id <id>` 重新轮询恢复。若用户放弃恢复，告知「因网络原因本次任务执行失败，相应点数已返还」并询问是否重试。 |

> 一句话：任务已发起但未成功产出报告（退出码 5、6，以及放弃恢复后的 124），统一告知用户「因网络原因本次任务执行失败，相应点数已返还」并询问是否重试；任务未发起到位的（2、3、4）不涉及扣点。

未知状态不要自行判定失败；脚本会原样透出 status，继续按轮询结果处理。
