# 任务拆解

## 拆解前的强制动作

**先写验收标准，再拆任务。**

顺序反了会产出「拆得很漂亮但没法验收」的节点。
先问「做到什么程度算完成」，得到 3~5 条可验证的句子，再往下拆。

## 每个子节点必须写全 5 个字段

| 字段 | 要求 | 反例 |
|---|---|---|
| title | 一个动作 + 一个对象 | ❌「优化性能」 ✅「把首屏加载从 3s 降到 1.5s」 |
| instructions | 具体到能照着做 | ❌「处理一下数据」 |
| acceptance | ≥1 条可验证句 | ❌「体验良好」 |
| dependsOn | 显式列上游节点 | 隐含依赖 = 后面必然乱 |
| 能力词 | 这个节点需要什么能力 | 用于主持自查有没有人能干 |

## 依赖规则

- **不许有环**。有环就是拆错了，不是执行难。
- **能并行的必须标成并行**（无依赖关系的节点不要串成一条链）。
- **共享写入的节点必须串行**。两个节点同时写同一个文件 = 必炸。
- 外部依赖（网络、需要凭据、需要用户配合）**显式标出来**，
  不要藏在 instructions 里。

## 能力自查（这是拆解的一部分，不是执行时的临场决定）

每个节点都要问一句：**有没有角色具备这个能力？**

没人具备 → 主持必须当场补救，三选一：
- 补技能（`skill-fetch`）
- 造角色（`role-forge`）
- 试一次，不行就标跳过并告知（**不许死循环补救**）

补救要一次做完，不要拆成额外的「补救任务节点」。

## 工作流

1. 写 3~5 条验收标准。
2. 按「验收标准」反推需要哪些产出物。
3. 一个产出物 = 一个节点（除非它小到不值得单列）。
4. 标依赖，检查无环。
5. 每个节点填 5 字段。
6. 逐节点做能力自查，缺能力当场补救。
7. **收敛**：把可以合并的节点合并。节点数 > 7 就该合了。

## 自检清单

- [ ] 验收标准写在拆解**之前**，且 ≥3 条
- [ ] 每条验收标准可验证（能写成 if-then 或可数可查）
- [ ] 每个节点 title 是「动作 + 对象」
- [ ] 每个节点 instructions 具体到能照着做
- [ ] 每个节点 acceptance 非空
- [ ] dependsOn 显式，依赖图**无环**
- [ ] 无依赖关系的节点已并行
- [ ] 共享写入的节点已串行
- [ ] 外部依赖（网络/凭据/用户配合）已显式标出
- [ ] 逐节点完成能力自查，缺口已补救或已标跳过
- [ ] 节点数 ≤7，或已说明为什么不能合并

## 交付时说清

节点数、依赖关系、有几个跳过及原因、补救了几处能力缺口。
