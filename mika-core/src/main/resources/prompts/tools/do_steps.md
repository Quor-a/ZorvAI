Run consecutive actions on one screen in one call when the element list already identifies the next targets (for example: tap a named field, type the whole value, tap another named field, type its whole value). Choose the number of steps from the task and known interface, up to the per-call resource limit. Each step is checked locally before the next; the batch stops when an action fails, the interface needs visual review, the app switches, or a step's wait condition is not met. When a step starts loading (search, submit, open a page) and the next step needs the result, give that step a condition instead of ending the batch to wait: expect (text it brings up), expect_gone (a loading label), expect_app (app package or page address) or wait_stable. The step then waits up to timeout_s (default 8) and stops early on a popup, a system dialog or another app; the result says how long it waited and why it stopped. Do not batch past a step whose outcome you must judge by looking (which item to pick, whether it worked); end the batch there. An unchanged screen alone does not mean the task is stuck. Inspect the final screen before deciding what to do next. All steps must act on the same screen (mixed_surface otherwise). Requested send, post, order, delete and pay actions can be included in a batch; read the resulting state before claiming success. Use only refs that were visible before the batch and still identify the same element; if the next target appears only after an action, stop and inspect the new screen.
