# 云端推理 · 思考与工具调用架构

> 与 `本地推理引擎思考与工具调用架构.md` 同构：那份修的是**端侧引擎**（MNN / llama.cpp），
> 这份修的是**云端 API**。两条链路常被混为一谈，但它们的缺口完全不同 ——
> 端侧缺的是「契约写了实现是空的」，云端缺的是「**请求侧参数根本不存在**」。

盘点时间 2026-10-01。所有「现状」均标注**实测行号**，不写推断。

## 零、盘点结论

### 0.1 三条链路的健康度极不均衡

| 环节 | 端侧（MNN/llama） | 云端（API） |
|---|---|---|
| **思考：请求侧控制** | ✅ 已补（N4/N9，三态 `thinkingMode` + 真实标签注入） | 🔴 **完全缺失** |
| **思考：解析/剥离** | ✅ 已补（N1–N3，native `ThinkSplitter` 权威分流） | ✅ **本来就完整**（三字段兼容 + `<think>` 状态机） |
| **思考：流式上屏** | ✅ `onThinking` 回调 | ✅ 已做（`QuroLlmClient.kt:862-865`） |
| **工具调用：请求侧下发** | ✅ `toolsJson` → 模板消费 | ✅ 已做，但 `tool_choice` **写死 auto** |
| **工具调用：流式拼接** | ✅ native 分流 | ✅ 已做（按 index 槽位累计，`:867-882`） |
| **工具调用：参数容错** | 靠 Kotlin 反解 | ✅ 已做（启发式修复非法 JSON，`:693-745`） |
| **Agent：循环与制动** | — | ✅ 已做（死循环滑动窗口 / 收尾提示 / 天花板） |
| **Agent：用量与停止原因** | — | 🔴 **`usage` / `finish_reason` 全部丢弃** |
| **Agent：错误分类** | — | 🔴 **只有一句错误文本，无分类无策略** |

### 0.2 🔴 核心缺口：请求侧零思考控制

`QuroLlmClient.chat()` 构造请求体的地方是 `:114-149`，逐字段看：

```
model / max_completion_tokens|max_tokens / temperature / messages / tools / tool_choice / stream
```

**没有任何一个字段与「思考」有关。** 这意味着：

- 「深度思考」开关打开后，云端请求**与关着时逐字节相同**。
- 它唯一的作用是 `QuroAssistant.kt:216-220` 往 system prompt 里塞一段自然语言：

  ```
  "\n\n## 深度思考（已开启）\n在回答前，请先进行充分、深入的内部思考…"
  ```

  该函数的注释**自己就写着**这是为了「弥补此前『深度思考』开关只控制 UI 显隐、
  从不真正影响模型行为的缺陷」—— 但它仍然只影响 prompt，**依然没管住 API 参数**。

后果，按模型家族分：

| 模型 | 开「深度思考」后的真实结果 |
|---|---|
| OpenAI o 系列 / GPT-5.x | **无变化**。GPT-5.x 默认推理档位随版本反复变（5→medium、5.1→none、5.5→medium），不显式设置就只能听天由命 |
| Anthropic Claude | **无变化**。不传 `thinking` 就不进思考模式，reasoning 块根本不会产生 |
| Qwen3（vLLM/SGLang/百炼） | **反向失效**。Qwen3 默认 `enable_thinking=true`，**无法关闭**；用户关掉开关，模型照样吐一大段思考 |
| DeepSeek-R1 / QwQ / GLM-Z1 | **无变化** |

也就是说：用户拨动开关，唯一变化的是 system prompt 多了一段话。

### 0.3 三个次级缺口

**① `isReasoningModel` 识别过窄**（`:108`）

```kotlin
val isReasoningModel = Regex("(?i)^o[0-9]").containsMatchIn(model.trim())
```

只认 `o1/o3/o4`。GPT-5 全系、DeepSeek-R1、QwQ、Qwen3、GLM-Z1、MiMo 等全部落入「普通模型」
分支 → 被发 `temperature` + `max_tokens`。而 GPT-5 系**不接受 `temperature`**，
Anthropic 开思考后**不能用 `temperature`/`top_p`** —— 这类请求会被上游判 400，
表现为「某些模型一选就报错」。

**② `usage` 与 `finish_reason` 全部丢弃**

`parse()`（`:618-663`）只取 `choices[0].message`，`usage` 与 `finish_reason` 读完即弃。
后果：

- 看不到 `completion_tokens_details.reasoning_tokens`（思考花了多少）、
  `prompt_tokens_details.cached_tokens`（缓存命中多少）→ 成本不可观测；
- `finish_reason == "length"` 说明回答被 `max_tokens` 腰斩，但循环不知道，用户只看到半截话；
- `finish_reason == "content_filter"` 被当成正常空回复。

**③ 工具失败无结构化分类**

`QuroAssistant.kt:841-856` 的 `Error` 分支与工具执行异常兜底
（`:691`、`:697`）都只产生**一句自由文本**回喂。业界最佳实践要求按错误类给策略：

```
ERR_INVALID_ARGS  → 把 schema 一起回喂，要求按 schema 重发
ERR_NOT_FOUND     → 先探测（列目录/查状态）再重试，禁止盲重试
ERR_PERMISSION    → 提示用户授权，不自动重试
ERR_TIMEOUT       → 允许降级参数重试一次
ERR_ENV_MISSING   → 触发对应环境装配
ERR_UNKNOWN       → 原样回喂，不编造原因
```

## 一、上游协议规范（2026-10 实测检索）

四家各说各话，**这是本方案必须做参数编译层的原因**。

### 1.1 OpenAI / 通用网关

| 参数 | 取值 | 备注 |
|---|---|---|
| `reasoning_effort` | `none` `minimal` `low` `medium` `high` `xhigh` `max` | 层级**不向下兼容**：老 GPT-5 收 `minimal`，新版改收 `none`，发错值上游报 `unsupported_value` |
| `reasoning: {effort}` | 同上 | 🔴 **与 `reasoning_effort` 互斥**，同一请求同时发二者 = 400 |
| `reasoning: {max_tokens}` | 正数 | 优先级**高于** effort；不传 effort 也可单独用 |
| `verbosity` | `low` `medium` `high` | GPT-5 系输出详略 |

⚠️ GPT-5.x 默认档位**跨版本反复变更**（5→medium、5.1→none、5.2→none、5.4→none、5.5→medium）。
→ **绝不能依赖默认值，必须显式下发。**

⚠️ GPT-5 系**不支持** `temperature`、`top_p`、`logprobs`。

### 1.2 Anthropic

| 形态 | 参数 |
|---|---|
| 手动固定预算 | `thinking: {type: "enabled", budget_tokens: N}` |
| 自适应（新） | `thinking: {type: "adaptive"}` |
| 显示控制 | `display: "summarized"` / `"omitted"` |

约束（**违反即 400**）：

- `budget_tokens >= 1024`，且**必须 < `max_tokens`**（交错思考例外）；
- 思考开启时**不兼容** `temperature` / `top_p` / `top_k`，也**不支持强制工具调用**；
- 思考块带 `signature` 字段，多轮与工具调用场景必须**原样回传**；
- 工具调用之间也能思考 = **interleaved thinking**，Claude 4 系需 beta header
  `interleaved-thinking-2025-05-14`；4.6 起 adaptive 模式自动交错；Opus 4.6 手动模式**完全不交错**；
- 流式事件名是 `thinking_delta`。

### 1.3 通义千问 Qwen3（国内主力）

| 部署形态 | 开关字段 |
|---|---|
| vLLM / SGLang（OpenAI 兼容） | `chat_template_kwargs: {enable_thinking: bool}` |
| DashScope OpenAI 兼容 | `enable_thinking: bool` |
| DashScope 原生 | `generate_cfg.enable_thinking` |

⚠️ Qwen3 **默认 `enable_thinking=true`** —— 反过来，用户想关思考时必须显式传 `false`。
⚠️ Qwen3 思考模式推荐采样参数：`temperature=0.6 / top_p=0.95 / top_k=20 / min_p=0`，**禁用贪心解码**。
⚠️ 部分服务端把思考与正文混在同一个 `content` 里（`think...回答`），
另有服务端已拆成独立 `reasoning_content` —— 解析侧必须两者都认（本仓已认）。

### 1.4 Google Gemini / 阿里 DashScope 原生

思考预算走 `reasoning.max_tokens`（网关翻译）或 `thinking_budget`（DashScope 原生）。

### 1.5 业界 Agent 循环最佳实践（检索综合）

- **硬终止契约**：`max_iterations` + 显式 `task_complete` 工具，**不靠自然语言「我做完了」**；
- **停止原因是头等字段**：每次运行记录 `stop_reason`，便于观测；
- **检查点压缩**：长任务要 compact state、把耐久产物放到上下文之外，防 **context rot**
  （上下文腐化：早期计划变陈旧、工具输出挤掉目标，模型开始优化「最近的文本」而非真实状态）；
- **no-progress 检测器 ≠ 验证器**：重复参数 / 重复状态哈希 / 切换态 / 不变化的错误类都要能识别；
- **并行不是免费的**：并行子代理增加协调、上下文装配、成本与失败面；父循环必须承担结果对账；
- **取消是一次真实的状态转移**：要停新工作、通知子任务、保留最后检查点、记录哪些副作用已完成。

## 三、方案

### 3.1 C1+C2：思考控制参数编译层（核心）

新增 `QuroReasoningControl`（纯逻辑、可单测，不依赖 Android）：

```kotlin
enum class ThinkingLevel { AUTO, OFF, MINIMAL, LOW, MEDIUM, HIGH }

data class ReasoningPlan(
    val reasoningEffort: String? = null,      // 顶层 reasoning_effort
    val reasoningObject: JSONObject? = null,  // reasoning: {effort|max_tokens}
    val thinkingObject: JSONObject? = null,   // thinking: {type,budget_tokens}
    val chatTemplateKwargs: JSONObject? = null,// chat_template_kwargs
    val topLevelEnableThinking: Boolean? = null,// 顶层 enable_thinking
    val suppressTemperature: Boolean = false, // 该档位下必须省略 temperature
    val suppressMaxTokens: Boolean = false,   // 必须用 max_completion_tokens
    val notes: List<String> = emptyList(),    // 诊断
)
```

编译规则（`thinkingLevel × provider × model` → `ReasoningPlan`）：

| 家族识别 | 下发字段 | 关思考时 | 开思考时 |
|---|---|---|---|
| `^(o[0-9]\|gpt-5)` | `reasoning_effort` | `none` | `low`/`medium`/`high` 按档 |
| `anthropic|claude` | `thinking:{type,budget_tokens}` | 不传（默认关） | `budget = maxTokens * 0.6`，钳到 `[1024, maxTokens-1024]` |
| `qwen3`（且非 dashscope 原生） | `chat_template_kwargs.enable_thinking` | `false` | `true` |
| `dashscope` 兼容端点 | 顶层 `enable_thinking` | `false` | `true` |
| `deepseek-r\|qwq\|glm-z\|magistral` | 不传（模型恒思考） | 不传，仅提示 | 不传 |
| 其它 | 不传 | — | — |

**互斥保证**：`reasoningEffort` 与 `reasoningObject` **永不同时非空**（编译期由单一函数产出，
并在 `QuroLlmClient` 加断言日志，绝不把 400 送给上游）。

**与 prompt 的关系**：`buildDeepThinkDirective` **保留**（对无原生开关的模型仍是唯一手段），
但不再假装它是全部 —— 注释要改写成「原生开关可用时以原生为准，prompt 为兜底」。

### 3.2 C3：`usage` / `finish_reason` 解析

`QuroLlmResult` 增加 `usage` 与 `finishReason`；流式路径从最终 chunk 收集。
循环接线：

- `finish_reason == "length"` → 提示「输出被 max_tokens 截断，可继续」而非当成完整答复；
- `finish_reason == "content_filter"` → 明确报错；
- `reasoning_tokens` 累计 → 诊断日志 + 可选 UI 展示。

### 3.3 C4：工具失败结构化分类

`QuroToolError` 分类器（在 `engine.execute` 结果上做文本→类映射），
每类附一条**回喂策略片段**追加到 tool 结果末尾，让模型知道下一步该干什么。

### 3.4 C5：`tool_choice` / `parallel_tool_calls` 可配

`QuroModelConfig` 增加两项；默认 `auto` + 不发送 `parallel_tool_calls`（保持现状兼容）。

### 3.5 C6/C7：压缩与回传策略

- C7 先做**保守修复**：把「是否回传 `reasoning_content`」改成按家族白名单（已知接受的才发），
  未知家族默认**不回传**（缺它只是损失一点连续性，多传它可能整轮 400）。
- C6 作为后置项（需要真机压测长任务）。

### 4.3 计划外发现的两处真实 bug（N5 改向的原因）

原计划 N5 只做 `tool_choice` 配置化。但在核对「工具规格如何下发到上游」时，
发现两处**静默**故障 —— 它们比原计划内容重要得多，因此 N5 改向。

**Bug 1 — 全中文技能名全部坍缩成同一个工具名（严重）**

`QuroSkill.sanitizeToolName` 把每个非 ASCII 字符替换成 `-`、折叠连续 `-`、去首尾，
空了回退 `"skill"`。于是：

```
「视频号账号诊断」→ 全是非 ASCII → 替换成 '-' → 折叠 → trim → "" → 回退 "skill"
「合同风险审查」  → 同上 → "skill"
「抖音热榜」      → 同上 → "skill"
```

三者都得到 `skill__skill`；紧接着 `QuroTool.specs()` 的 `distinctBy { it.name }`
把它们**去重到只剩一个**。

> **用户装了 N 个中文技能，AI 实际只能调用其中 1 个，且没有任何日志或提示。**

修法：把净化委托给 `QuroToolSpecGuard.sanitizeName` —— 只要净化过程中发生
**信息丢失**（字符丢失 **或** 长度丢失），就追加 `-<原名 SHA-256 前 8 位>`，
唯一性恢复；同时把总长压进 64 字符（OpenAI function name 上限，超了整段 `tools` 被拒收）。

> 实现细节：丢失检测必须同时看**两种**丢失。只查「净化结果 ≠ 原文」会漏掉
> **纯 ASCII 超长名**（它两者相同），截断后两个共享长前缀的名字会直接撞名 ——
> 这一点是被单测抓出来的（见 `共享长前缀的名字截断后不撞名`）。

**Bug 2 — 一条坏记录让全部导入工具静默消失**

`QuroImportedToolRegistry.load()` 用**一个** `runCatching` 包住了**整个 for 循环**：

```kotlin
runCatching {
    for (i in 0 until arr.length()) { ... }   // ← 任意一条抛异常，整个循环中断
}
```

任意一条记录畸形（缺 `name`、类型不对）→ load 提前退出 → 后面**所有**导入工具都不加载。
用户表现是「我导入的工具全没了」，而日志里连一行错误都没有。

修法：逐条容错（坏记录单独跳过并计数告警）+ 名字入库即净化。

**这两条与 N1–N4 修的问题是不同性质**：

- N1–N4 修的是「**功能无效**」——参数缺失 / 信号被丢弃，功能在但不好用；
- Bug 1 / Bug 2 是「**功能消失**」——供应链静默丢数据，功能直接不见了。

后者更难发现：没有报错、没有日志、没有异常，用户只会觉得「这个 App 怎么总有些东西用不了」。

### 4.4 N10–N12：端侧（MNN / llama.cpp）工具调用与思考（2026-10-01 追加）

触发：用户真机实测后贴回的报错原文 ——

> 模型尝试调用工具但输出格式不规范，本次未能执行（文本中出现工具调用特征，但没有找到可解析的 JSON 对象）。
> 该模型可能未针对工具调用训练，建议在模型配置里关闭「本地工具调用」

外加两条 UI 症状：「对话框不支持 MNN + llama.cpp 的思考」「工具调用在对话框显示在标签」。

#### 根因（三症状同源）

| 症状 | 根因 | 定位 |
|---|---|---|
| 报错原文 | 旧解析器只认**严格合法 JSON**；裸键名 / 单引号 / 尾随逗号 / 缺闭合 / 函数式调用**全部落空**，且三条路径都没记录失败原因 → 只剩那条兜底文案 | `QuroLocalToolsCodec.parseDetailed`（旧实现） |
| 标签上屏 | 解析失败分支把**仍含 `<tool_call>` 的原文**连同警告一起 `onToken` 推给 UI；解析成功分支推的同样是带标记的原文 | `QuroLocalEngineNative` MNN / llama 两处 |
| 思考不显示 | `if (!thinking)` 把 reasoning 从所有气泡剔除，而 `thinking` 是**云端**「深度思考」开关（映射 `reasoning_effort`），端侧根本不消费它 | `ChatScreen.kt` 聚合段 |

#### 交付

- **N10 `QuroToolCallRepair`（新建）**：容错解析层。
  - 核心是**宽松 JSON 解析器 `LooseJson`**：单引号、裸键名、裸值、尾随逗号、缺闭合括号、
    字符串内裸换行、全角标点、`True/None/undefined` 全部容忍；解析只在 EOF 处收束，
    遇意外字符"跳过并继续"而不是抛异常。
  - 多标签族：`<tool_call>` / `<tool_calls>` / `<function_call>` / `<|tool_call|>` / `[TOOL_CALLS]`。
  - 参数形态归一：`arguments` / `parameters` / `args` / `params` / `input` / `action_input` … 别名，
    以及**参数摊平到顶层**（`{"name":"read_file","path":"/a.txt"}`）。
  - 函数式调用：`read_file(path="/a.txt")` / `get_time()` / `read_file({...})`。
  - **工具名纠错**：完全一致 → 归一化一致（忽略大小写 / 下划线）→ 编辑距离 ≤ `min(3, len/4)`；
    并列歧义时**放弃纠正**（绝不瞎猜），无近似则保留原名交由引擎报 `NOT_FOUND`。
  - 去重按 `(name, arguments)`——`<tool_calls>` wrapper 与内层 `<tool_call>` 会产出同一段 JSON，
    不去重会把有副作用的工具执行两遍；**信封里模型给的 id 原样保留**（它是 tool 结果回填的配对键）。
  - `sanitizeVisible`：从可见正文剥离全部调用标记（含只开不闭的截断层；围栏块仅在内容确为调用时才剥）。

- **N11 接线**：`parseDetailed(raw, knownNames)` 委托新层；`toolNamesOf(toolsJson)` 取本轮下发的
  名集合供纠错；`sanitizeForDisplay` 在两条引擎路径**推屏前**剥标记 —— 解析仍用带标记的原文，
  反过来先洗原文会让 `<tool_call>` 再也找不到。
  失败提示从"该模型可能未针对工具调用训练，建议关闭功能"改为**三条可操作建议**
  （降温 / 换模型 / 关功能）——因为这个分支现在只有在真难救时才会走到。

- **N11b（借鉴 PokeClaw 的 harness 实践）**：降级注入的 system 指令补**具体示例** ——
  用列表里第一个真实工具名 + 按 schema `required` 生成的参数骨架，并显式标注
  「format only — do NOT copy the function name」。
  只给占位符时，小模型的典型失败是**原样照抄 `<function-name>`**。

- **N12 思考展示解耦 + 温度收敛**：
  - `ChatScreen` 的 reasoning 剔除条件加 `&& !localEngine`：端侧产出的思考段不再被云端开关
    连带丢弃（该开关的语义是"要不要命令它想得更深"，不等于"不许展示思考"）。
  - llama 路径在**带工具定义的那一轮**把温度收敛到 ≤ 0.3（`TOOL_CALL_MAX_TEMPERATURE`）。
    依据：PokeClaw 在 LiteRT-LM 上跑 Gemma 4 做工具调用直接用 0.1 —— 采样越随机，
    越容易在 JSON 结构字符上抖出畸形形态，再强的解析层也救不回来。
    MNN 侧温度由模型自带 `llm_config.json` 决定，引擎层没有参数可收敛。

#### 验收

  （正文里的普通 JSON 不得被当成调用）、名称纠错三级匹配、去重、正文清洗。

## 五、与端侧那套的关系

两份文档是**同一构想的两个后端**：

```
             ┌──────────────────────────────┐
             │  上层：QuroAssistant 循环     │  ← 共用（工具执行/制动/回喂）
             └───────────┬──────────────────┘
                         │ QuroModelConfig + ThinkingLevel
         ┌───────────────┴───────────────┐
         ▼                               ▼
  云端 QuroLlmClient              本地 QuroLocalEngine*
  ← 本文档                        ← 本地推理引擎…架构.md
  缺：请求侧参数编译               缺：曾为思考契约空实现（已补 N1–N9）
```

**共同原则**（两轮都在用，值得固化）：

1. **能力探测优先于硬编码名单** —— 端侧读 `jinja.chat_template` 探测，云端按家族+端点特征编译；
2. **探测不到时什么都不做**，保持与改动前完全一致（端侧 `addMarkers` 空集即 no-op，云端不传未知字段）；
3. **幂等/可重入** —— 端侧每轮渲染都调 `addMarkers`，云端每轮都重新编译 plan；
4. **绝不因「猜错了」把 400 送给上游** —— 宁可少传一个字段。
