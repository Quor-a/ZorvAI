# 本地推理引擎（MNN + llama.cpp）思考与工具调用架构

> 2026-10-01 · 全部结论来自**实测代码**，每条都附文件:行号。
> 这是当前 native 侧最实的两块缺口。

---

## 一、思考（reasoning）架构：契约写了，实现是空的

### 1.1 硬证据

**引擎契约层声明了分流能力**：

```cpp
// llm/core/include/quro/engine_types.h:109
struct TokenChunk {
    const char* text = nullptr;
    size_t len = 0;
    bool isThinking = false;      // 思考段（<think>）与正文分流
};
```

**但两栈所有 chunk 发射点全部硬编码 `= false`**：

| 位置 | 代码 |
|---|---|
| `llama_engine.cpp:611` | `chunk.isThinking = false;` |
| `llama_engine_generate.cpp:478` | `chunk.isThinking = false;` |
| `llama_engine_generate.cpp:528` | `chunk.isThinking = false;` |
| `mnn_engine_generate.cpp:85` | `chunk.isThinking = false;` |

全仓 `grep isThinking` → **没有任何一处置 `true`**。
Kotlin 侧（`app/src/main/java`）对 `isThinking` 的引用数 = **0**。

> **契约声明了「思考段与正文分流」，实现层零实现，消费层零消费。**

### 1.2 后果：同一件事被迫在 Kotlin 里实现三遍

因为 native 不做分流，只能在上层用文本手段补：

| 补偿实现 | 位置 | 做什么 |
|---|---|---|
| `StreamingThinkStripper` | `QuroLocalEngineNative.kt:35`（约 110 行文本状态机） | 流式剥离 `<think>…</think>`；含**全角标签归一化**（`＜think＞`→`<think>`）、**未闭合标签的尾部暂缓提交**、**标签跨 token 边界检测** |
| `MnnThinkContent.split()` | `llm/mnn/.../MnnThinkContent.kt:48` | 终态再切一次 |
| `stripResidualThink` | `QuroLocalEngineNative.kt:162` | 再兜一遍残留标签 |

这三层叠起来就是「思考构架」的**实际形态**——**文本正则状态机**，而不是引擎层的结构化分流。
代价：

1. **边界漏洞必然存在**。`QuroLocalEngineNative.kt:193` 的注释自己写着：
   *「StreamingThinkStripper / stripResidualThink 只认 `<think>` 标签，对这种**无标签明文推理**完全失效」*
   —— 也就是换一个不带标签的思考模型，整套剥离直接失效。
2. **两端各写一套**，行为不一致（MNN 走 `MnnThinkContent`，llama 走别的路径）。
3. **思考段与工具调用的交互无人建模**（见 §2.3）。

### 1.3 能力不对称

| | MNN | llama |
|---|---|---|
| 思考模式开关 | ✅ `MNNLlmSession.setThinkingMode(enabled)`（走 jinja `enable_thinking`） | ❌ **`LlamaNative` 14 个方法里完全没有** |
| 思考内容分流通路 | ⚠️ 有 `onThinking` 回调，但靠文本剥离产生 | ⚠️ 同上 |

驱动层 `onThinking` 回调是**引擎无关**的（`runMnn` / `runLlama` 都传），
但 llama 路径根本没有产生思考内容的手段。

## 二、工具调用架构：两端不对称 + 最有效的入口不可达

### 2.1 能力对照

| 能力 | llama | MNN |
|---|---|---|
| 工具定义渲染 | ✅ `nativeApplyStructuredChatTemplate` | ✅ `applyChatTemplateStructured` |
| 输出反解成 OpenAI `tool_calls` | ✅ `nativeParseToolCallResponse` | ❌ **无** |
| **GBNF 文法约束**（把 JSON 错误率压到 ~0） | ⚠️ **native 实现了，但 Kotlin 不可达** | ❌ 不支持 grammar |

### 2.2 「最有效的入口不可达」——本段最关键的发现

- native 侧 **有完整实现**：`LlamaEngine::setToolCallGrammar(grammar, triggerPatterns, err)`
  （`llama_engine_chat.cpp:98`，含惰性触发、事务语义回滚、`common_chat_parser_params` 装配）。
- Kotlin 侧 **只有清除入口，没有设置入口**：
  ```
  LlamaNative.kt:84   external fun nativeClearToolCallGrammar(sessionPtr: Long): Boolean
  ```
  `grep nativeSetToolCallGrammar` → **零命中**。

> 也就是说：**语法约束这条「把 JSON 解析错误率从 15–25% 压到接近 0」的路径，
> 在 native 里造好了轮子，却没接上方向盘。**

驱动层注释自己承认了这点：

> `QuroLocalEngineNative.kt:374`
> 「工具调用（grammar）走 llama 的 applyStructuredChatTemplate，**归 Phase 3 流式/工具链接入**」

### 2.3 思考段 × 工具调用的交互没建模

> `QuroLocalEngineNative.kt:1127`
> 「结构化路径：原生 parseToolCallResponse 优先；**未命中（模板无 parser / 思考段内 `<tool_call>`）**」

这句话暴露了一个真实漏洞：**模型把 `<tool_call>` 写在思考段里时，两条路径谁都接不住**：
- `StreamingThinkStripper` 认为它在思考段内 → **当思考内容丢掉**
- `parseToolCallResponse` 只解析正文 → **看不到它**

### 2.4 MNN 侧没有反解器

> `QuroLocalEngineNative.kt:575`
> 「**MNN 原生无 parseToolCallResponse**，回调收到的是 raw 模型文本（含 `<tool_call>` 标签）」

于是 MNN 的工具调用要靠 Kotlin 的 `QuroLocalToolsCodec` 兜底解析 ——
同一件事（工具调用反解）又是两端两套。

## 三、方案

### 3.1 思考分流上移到 native（核心）

**新增 `llm/core/` 里的引擎无关思考段状态机**（纯 C++、零依赖、可单测）：

```
llm/core/include/quro/think_splitter.h   +  src/think_splitter.cpp
```

**为什么放 core 而不是各引擎一份**：
- 两端共用 → 消掉 Kotlin 那三份重复实现，行为强制一致
- `isThinking` 契约在**引擎边界**就被满足，上层不需要文本解析
- 可单测（现有 `llm/core` 有单测基建）

**必须把 Kotlin 那三份实现里的真机教训逐条搬进 C++（否则会重犯同样的 bug）**：

1. **全角标签归一化**：`＜think＞ → <think>`（`QuroLocalEngineNative.kt:72` 的注释说明模型会吐全角）
2. **未闭合标签的尾部「暂缓提交」**：不能把可能构成标签前缀的字符提前发出去
   （否则 UI 上会闪过 `<thi`）
3. **标签跨 token 边界**：token 是任意字节切片，标签可能被切开
4. **UTF-8 跨 token 边界**：与现有 `utf8CharLength` 缓冲配合
5. **可配的起始标记集合**：不只认 `<think>`，要能配 `思考`、`<|think|>`、`reasoning` 等
   —— 这是解决「无标签明文推理完全失效」的入口
6. **思考段内的 `<tool_call>` 必须保留**（见 3.3）

**接线**：
- llama：`llama_engine_generate.cpp` 发 chunk 前过 splitter，`chunk.isThinking` 如实填
- MNN：`mnn_engine_generate.cpp` 的 `CallbackStreamBuf` 内分流（同一份状态机）
- Kotlin：`StreamingThinkStripper` **降级为纯兼容 fallback**（只在 native 未识别时兜底），
  正常路径直接消费 `isThinking` 标志

### 3.2 llama 侧补思考模式开关

- `LlamaNative.nativeSetThinkingMode(sessionPtr, enabled)` → `LlamaEngine::setThinkingMode`
- 实现走 llama.cpp 的 jinja `chat_template_kwargs` / `enable_thinking`，**与 MNN 语义对齐**
  （MNN 侧已有 `setThinkingMode`，走 `jinja.context.enable_thinking`）

### 3.3 工具调用架构补齐

**① llama：把 GBNF 入口接出来（最高性价比）**
- `LlamaNative.nativeSetToolCallGrammar(sessionPtr, grammar, triggerPatterns): Boolean`
- `LlamaSession.setToolCallGrammar(...)`
- 上层在工具轮**真的把 JSON Schema 编译成 GBNF 下发** → JSON 解析错误率 15–25% → ~0%

**② MNN：补引擎无关的工具调用反解器**
- 在 `llm/core/` 写 `tool_call_parser`：吃原始文本，识别
  `<tool_call>{...}</tool_call>` / Hermes / Mistral / Qwen 等常见格式 → 统一 OpenAI JSON
- llama 侧也可用它作为 `parseToolCallResponse` 未命中时的**第二级兜底**
- 收益：MNN 不再依赖 Kotlin 侧解析，两端行为一致

**③ 思考段 × 工具调用 的交互规则（明确化）**
```
思考段内发现的 <tool_call>  →  保留，交给工具解析器（绝不能当思考丢掉）
正文段内发现的 <tool_call>  →  同上
思考段内发现的不完整 JSON    →  继续缓冲，直到闭合或生成结束
```
光有规则不够，**必须有回归用例**（这是当前已知的真实漏网场景）。

**④ 流式工具调用增量解析**
半截 JSON 不上屏、不误判为无工具调用。

## 六、实施进度与实测结果（2026-10-01 更新）

### ✅ N1 · 引擎无关思考分流器 —— 已完成并验证

新增 `llm/core/{include/quro/think_splitter.h, src/think_splitter.cpp, test/think_splitter_test.cpp}`，
接入 `llm/core/CMakeLists.txt`。

**验证手段（这是本次最重要的基建）**：宿主 Windows 没有 g++/clang/cl，
NDK 的 clang 只有 Android target 头（编宿主程序报 `'string' file not found`）。
改用 **zig 当宿主编译器**：

    pip download ziglang -d /d/zigpkg -i https://mirrors.aliyun.com/pypi/simple/ --no-deps --only-binary=:all:
    zig c++ -std=c++17 -O2 -Wno-nullability-completeness -I <inc> a.cpp b.cpp -o out.exe

（**只有阿里云镜像有 `ziglang`**，清华/腾讯都返回 No matching distribution。）

**结果：209 条断言 0 失败**，其中价值最高的是**任意切分不变性** ——
每个用例都按 1..9 字节逐切片喂进去，结果必须与整串喂入**完全一致**
（token 边界不可控，这是唯一能证明状态机真的健壮的测法）。

**性能实测**（1 MiB / 4 字节切片；输入刻意选**最坏形态**：大量全角标点，
其首字节 0xEF 与全角标签 ＜think 相同，每个标点都会让扫描停一次）：

| 场景 | 优化前 | 优化后 | 提升 |
| --- | --- | --- | --- |
| A 纯正文 | 170.46 ms · 5.9 MB/s | **14.23 ms · 70.3 MB/s** | **12.0×** |
| B 含标签 + 思考段内工具调用 | 199.64 ms · 5.0 MB/s | **17.13 ms · 58.4 MB/s** | **11.7×** |

优化根因**不在状态机判断**，而在热路径的 malloc/free：
`matchAt`/`nextPossibleStart` 每次 feed 都现场新建 vector + 拷贝候选 + `stable_sort`；
`emit` 收 `const std::string&` 而调用点传 `pending_.substr()`。
1 MiB / 4 字节 = 26 万次 feed → 上百万次 malloc/free。改法：
① 候选列表 → 常驻 `expected_`，只在**段切换时**重建+排序；
② 首字节 → `firstByteTable_[256]` 查表，短 buffer 逐字节查表、长 buffer 才走 `memchr`；
③ `emit` 改收 `std::string_view`。
缓存**存下标不存指针** —— 本类在 `Session` 里是值成员，存指针会在 Session 拷贝后悬垂。

### ✅ N2 · 两栈接线 —— 已完成并验证

- 两栈 `Session` 各挂一个 `ThinkSplitter`，四个 chunk 发射点全部改为过分流器；
  **`isThinking = true` 首次真正出现在代码库里**。
- **5 处 reset**（这是必须的，见 §七 bug 3）：
  `llama_engine_generate.cpp:101`（`generate()` 开头，llama 唯一生成入口）、
  `llama_engine.cpp:318`(releaseResources) / `:711`(resetKv)、
  `mnn_engine_generate.cpp:262`（`runStreamCore` 的 `if (resetFirst)` 分支）、
  `mnn_engine.cpp:314`(resetKv)。
  MNN 的判据与 KV **完全一致**：`decode` 传 `resetFirst=false` 是同一轮的后半段，**绝不能**复位。
- **产物级验收**：`libLlamaWrapper.so` / `libMNNWrapper.so` 导出符号各 **= 1**（仅 `JNI_OnLoad`，
  符号隔离守住）；两者 `ThinkSplitter` 相关符号各 **32 个**；
  llama 侧可见 `emitThroughThinkSplitter`、MNN 侧可见 `mnn_detail::emitThinkSplit`。
- `llm/core` 用 NDK 工具链单独 cmake+ninja 编译：**10/10 通过**，`-Wall -Wextra` 无警告。

### ✅ N3 · 思考段上行打通 —— 已完成并验证

**为什么 N2 单独立不住**：引擎侧开始吃掉 `<think>` 标签并把内容分成两个通道，
而 Kotlin 侧的 `StreamingThinkStripper` 是**靠标签**分流的 ——
标签被吃掉、`isThinking` 又没人读，思考原文会被当成正文**实时上屏**（回归）。
所以 N2 必须连着 N3 一起上。

- **JNI 层**（`llama_jni.cpp` / `mnn_jni.cpp`）：`sinkOnToken` 按 `chunk.isThinking` 路由 ——
  首选 Java 的 `onThinking(String):Boolean`；
  **找不到该方法时把思考内容包回 `<think>…</think>` 再走 onToken**，让上层剥离器照常工作。
  两条路都不会让思考原文裸奔。
- **Kotlin 4 层**：`GenerationCallback` 接口（`onThinking` 声明为**抽象方法**）→
  `LlamaSession` / `MNNLlmSession` 会话方法 → `QuroLocalEngineNative` 驱动层 4 个调用点。
  接口用抽象方法而非默认实现，是为了让**所有实现类编译报错**，编译器帮我们查全；
  同时避开"Kotlin 接口默认实现在旧 `-Xjvm-default` 模式下未 override 会抛
  AbstractMethodError"这个隐患。
  会话层新参数插在 `onToken` **之前**，保住 trailing lambda 的绑定不变，老调用点零改动。
- **字节码级验收**（javap，决定性证据）：

      MNNLlmSession$guardedCallback$1:  public boolean onThinking(java.lang.String);
      LlamaSession$generateStream$2:    public boolean onThinking(java.lang.String);
      LlamaNative$GenerationCallback:   public abstract boolean onThinking(java.lang.String);

  与 JNI 探测用的 `onThinking(Ljava/lang/String;)Z` **完全匹配**，
  证明 `GetMethodID` 一定能找到并成功调用。

## 七、实施中抓到的 3 个真 bug（都是"看起来对"的那种）

### bug 1 · 嵌套类默认实参：这段代码从没被编译过

    explicit ThinkSplitter(Config config = Config());
    error: default member initializer for 'emitThinking' needed within definition
           of enclosing class 'ThinkSplitter' outside of member functions

C++ 硬规则：**嵌套类（Config）的默认成员初始化器不能在外围类定义内部被求值**，
而默认实参 `Config()` 正是在那里求值。
修法：拆成 `ThinkSplitter();` + `explicit ThinkSplitter(Config config);`。

**教训**：没有编译器的环境里，"写完"和"能编译"是两件事。

### bug 2 · Visible 段误吞 `<tool_call>`（性能优化时自己引入的）

把 tool_call 边界标记并进统一存储 `markers_` 后，`rebuildExpected` 用 `open`
布尔值一刀切筛候选 → **Visible 段也把 `<tool_call>` 当成了候选边界**
→ `applyMatch` 在 Visible 段没有对应动作 → **标签被静默吞掉**。

实测 1 MiB 用例里 visible 少 **82984** 字节 = 7544 个单元 × 11 字节（`<tool_call>`），完全吻合。

🔴 **当时 200 条断言仍然全绿** —— 因为原有断言只覆盖"思考段内"的工具调用，
"正文段内"这条路径根本没人守。**是靠性能用例打印的 visible 字节数与上一次不一致才发现的。**

修法：显式排除 `toolOpenIndex_`/`toolCloseIndex_`
（tool_call 边界的语义与 `open` 布尔值是**正交**的），
并在 `applyMatch` 补"绝不丢字节"兜底分支；同时补了 `caseToolCallInVisible` 4 组用例。

**教训**：一个"看起来更统一"的重构，会把某段独有的语义悄悄放宽。
必须为**每个段的每种标记组合**都留一条断言。

### bug 3 · 每轮生成未复位分流器（语义 bug，症状是"AI 不回复了"）

上一轮若在思考段中途结束（模型没吐 `</think>`，或被 maxTokens 截断），
`segment_` 会残留为 `Thinking` → **下一轮正文被整段判成思考** → 正文通道为空。

Session 跨轮复用、只构造一次，所以不能靠构造函数复位 —— 必须在每轮生成入口复位（见 §六 N2 的 5 处）。

**教训**：任何"跨轮复用的状态机"都要先问一句"它的生命周期是哪一段"，
并在那个生命周期的起点显式复位。
