## 一、A 线设计：端侧真 Gradle / CMake / NDK

### 1.1 总原则

1. **绝不在 Android 原生进程里跑 Gradle**。JVM 需要完整 Linux ABI、`fork/exec`、`/proc` 语义，
   一律走 **proot 容器**（已有基建）。
2. **环境按需装配 + 幂等探测**。`checkCmd` 只验关键二进制，已就绪就跳过重装
   （沿用 `EnvProfile` 既有契约）。
3. **诚实失败**。SDK license 未接受、aapt2 不匹配、内存不足、OOM killed ——
   一律回传**原始日志**，绝不编造成功（沿用 `build_apk` 的既定纪律）。
4. **不污染用户工程**。所有 ARM64 覆盖走 **Gradle init script**（进程级注入），
   而不是去改用户工程的 `local.properties` / `gradle.properties`。

### 1.2 关键坑与解法（这一节是全案最值钱的部分）

#### 🔴 坑 1：Google 的 `aapt2` 是 x86_64，ARM64 上必挂

这是端侧 Gradle 构建**第一杀手**。AGP 默认从 Maven 拉 `aapt2-<ver>-linux.jar`，
里面是 **x86_64 二进制**，ARM64 上直接 `cannot execute: required file not found`
或 `LoadedArsc.cpp:94 RES_TABLE_TYPE_TYPE entry offsets overlap actual entry data`。

三条已知解法（按可靠性排序）：

| 解法 | 做法 | 评价 |
|---|---|---|
| **A. init script 注入 `aapt2FromMavenOverride`** | 在 `~/.gradle/init.d/quro-arm64.gradle` 里对**所有工程**注入 `android.aapt2FromMavenOverride=/opt/android/aapt2` | ✅ **首选**。进程级生效，不碰用户工程 |
| B. 替换 Gradle 缓存里的 jar | `find ~/.gradle -name 'aapt2-*-linux.jar' \| xargs -I{} jar -u -f {} -C /usr/bin aapt2` | ⚠️ 清缓存即失效，需每次重建后重跑 |
| C. 改工程 `gradle.properties` | 往每个工程写一行 | ❌ 污染用户工程，AI 生成的工程可能被覆盖 |

**ARM64 aapt2 来源**（两个都记下来，互为备份）：
- `ReVanced/aapt2` releases → `aapt2-arm64-v8a`（构建于 build-tools 35.0.2）
- `lzhiyong/android-sdk-tools` releases → `android-sdk-tools-static-aarch64.zip`
  （含 `aapt aapt2 aidl apksigner zipalign` **全套**）

#### 🔴 坑 2：NDK 的 `toolchains/llvm/prebuilt/` 只有 `linux-x86_64`

官方 NDK 的 prebuilt 宿主是 `linux-x86_64` / `darwin-x86_64` / `windows-x86_64`，
**没有 `linux-aarch64`**。ARM64 设备上直接跑不了。

**务实解法（三层降级）**：

| 场景 | 方案 | 需要下载 |
|---|---|---|
| **纯 Java/Kotlin 工程**（AI 生成的绝大多数） | 不需要 NDK | 无 |
| **要 JNI 但用预编译 .so** | 设备上用**系统 clang + NDK sysroot** 编出 `lib*.so`，放进 `jniLibs/arm64-v8a/`；**AGP 只负责打包，不需要 NDK** | 只要 sysroot |
| **要跑 `externalNativeBuild`（CMake）** | 必须吃 **aarch64 Linux 版 NDK**（`0xLnxi/ndk-aarch64-linux` r27d / `chmod-x-Tieupsh/android-ndk-aarch64`） | ~3GB，**按需下载 + 缓存** |

**「系统 clang + NDK sysroot」的具体姿势**（`zongou/android-dev` / `chmod-x-Tieupsh` 方案）：

```sh
TOOLCHAIN="$NDK/toolchains/llvm/prebuilt/linux-x86_64"
clang \
  -resource-dir "$TOOLCHAIN/lib/clang/<ver>" \
  --sysroot="$TOOLCHAIN/sysroot" \
  --target=aarch64-linux-android<API> \
  -rtlib=compiler-rt -unwindlib=platform \
  -shared -fPIC foo.c -o libfoo.so
```

> **核心洞察**：关键不是 clang 二进制，而是 **sysroot + resource-dir + target triple**。
> 宿主 clang 只要版本不低于 NDK 自带 clang，就能用 NDK 的 sysroot 产出正确的 Android ELF。
> 这条使「设备上编 .so」**零下载**成立，从而绕开 3GB NDK。

#### 坑 3：`sdkmanager` 的 `emulator` 包在 ARM 上缺失

`build-tools;30.0.2` 及更早会因依赖 `emulator` 而装不上。
**解法：`buildToolsVersion ≥ 32`**，并在 `init.d` 里对所有工程强制统一 buildTools 版本
（避免某个第三方库把版本拉回 30）。

#### 坑 4：JVM target 不一致

Kotlin 编译若用一套 JDK、Java 用另一套，报 `jvmTarget` 不匹配。
**解法：`init.d` 里统一 `JavaVersion.VERSION_17` + `kotlin { jvmToolchain(17) }`**。

#### 坑 5：`proot` 下 Gradle daemon

Gradle daemon 会 fork 常驻进程，proot 下容易残留/串味。
**解法：默认 `--no-daemon`**，并把 `GRADLE_USER_HOME` 固定到容器内路径便于复用缓存。

### 1.3 落地结构

```
EnvProfile.ANDROID            ← 新增（CmsEnvProvisioner）
  checkCmd:      aapt2 + sdkmanager + java + gradle 存在
  installScript: JDK17/Gradle（复用既有 robust_install）
                 + 下载 cmdline-tools → sdkmanager 装 platform+build-tools
                 + 下载 ARM64 aapt2 覆盖
                 + 写 ~/.gradle/init.d/quro-arm64.gradle

android_build                 ← 新增工具（L2 编排）
  参数: project_path / task / variant / ndk_mode / extra_args / timeout
  流程: 探测环境 → (按需装配) → 写 init script → 容器内跑 ./gradlew
        → 流式回传日志（节流）→ 定位产物 APK → 返回真实路径 + 日志尾部
  纪律: 环境缺什么就说什么，缺 license 就提示，缺内存就说 OOM，绝不假装成功

android_sdk                   ← 新增工具（环境体检/修复，可选）
  查: SDK platform/build-tools/aapt2 架构/NDK 版本/磁盘余量
```

## 二、B 线设计：思考与工具调用构架补齐

业界 2025 的共识是在 ReAct（TAO：Think→Act→Observe）之上**再叠三层**。
本仓 ReAct 已扎实，缺的正是这三层。

### 2.1 Planning（任务分解）

- 现状：`TaskPlanner` 死代码。
- 目标：**首轮**把复杂请求分解为可验证的步骤清单，注入为隐藏 system 提示；
  执行中按步勾对，偏离时重新规划。
- 纪律：**只在真正复杂时触发**（多步/多文件/需验证），简单问答不触发 ——
  否则每轮多烧一次推理，用户会立刻感觉到变慢。

### 2.2 Reflection（生成 → 批判 → 精炼）

- 现状：**完全没有**。
- 目标：对**高价值产出**（代码、文档、架构方案）走 Evaluator-Optimizer：
  初稿 → 换视角批判（按维度逼问：边界条件？错误处理？可复现？）→ 精炼。
- 纪律：**不能对每轮回复都做**。只在（a）用户显式要求，或（b）产出被判定为
  「可交付物」时触发。批判必须**按维度**，泛泛"看起来还行"无价值。

### 2.3 Verification（外部验证器）

- 现状：`Verifier` 死代码。
- 目标：**工具自报成功 ≠ 成功**。按工具类别挂验证器：
  | 工具类别 | 验证方式 |
  |---|---|
  | 写文件 | 回读 + 长度/哈希校验 |
  | 构建 | 检查产物文件**真实存在且非 0 字节** + 签名可验证 |
  | 命令执行 | 退出码 + stderr 非空判定 |
  | 网络请求 | 状态码 + 结构校验 |
- 这是**「有 bug」类抱怨的直接解药**：多数"AI 说做完了但其实没做"都源于缺这一层。

### 2.4 工具调用构架（对照业界最佳实践补缺）

已有：ReAct、并行调用、渐进披露、权限闸门、能力目录。

**缺 1：Schema 合规审计**（可立即做，纯静态，零风险）
对 151 个工具做一次体检，按业界实证规则报告：
- `description` 是否**情境导向**（"当用户询问 X 时使用"）而非功能导向（"查询 X 数据库"）
  ——Gorilla/ToolAlpaca 实测：描述精确度与调用准确率强正相关
- 参数个数是否 ≤ 8（超过显著抬高认知负担）
- 嵌套是否 ≤ 3 层
- 离散型参数是否用了 `enum` 约束
- `required` 是否全必填（全必填会降低调用灵活度）
- `name` 是否 snake_case、动词在前

**缺 2：工具失败的结构化反馈回路**
现在只把错误文本塞回去。应做**错误分类 + 策略**：
```
ERR_INVALID_ARGS   → 把 schema 一起回喂，要求按 schema 重发
ERR_NOT_FOUND      → 让模型先探测（列目录/查状态）再重试，禁止盲重试
ERR_PERMISSION     → 提示用户授权，不自动重试
ERR_TIMEOUT        → 允许降级参数（更小范围/更短任务）重试一次
ERR_ENV_MISSING    → 触发对应环境装配
ERR_UNKNOWN        → 原样回喂，不编造原因
```

**缺 3：受约束解码**
本仓有本地引擎（llama.cpp / MNN）。llama 侧已有 `setToolCallGrammar` 接口 →
**工具调用轮应真的把 JSON Schema 编译成 GBNF 文法下发**，把 JSON 解析错误率从
15–25% 压到 ~0%。这是「深度优化」最有性价比的一项。

## 三、分期与验收

| 期 | 内容 | 验收标准（可实测） |
|---|---|---|
| **P1** | `EnvProfile.ANDROID` + `android_sdk` 体检工具 | 容器内 `aapt2 version` 输出 ARM64；`sdkmanager` 可列包 |
| **P2** | `android_build` 工具（纯 Java/Kotlin 工程） | 一个真 Gradle 工程在设备上 `assembleDebug` 出 APK，路径真实存在 |
| **P3** | JNI 支持（系统 clang + NDK sysroot） | 设备上编出可用 `lib*.so`，塞进 `jniLibs` 后 AGP 打包成功 |
| **P4** | NDK 按需下载（`externalNativeBuild` 场景） | CMake 工程能过 `configure` + 编译 |
| **P5** | 工具 Schema 审计 + 修复 | 产出审计报告，按规则修 description/enum/required |
| **P6** | Verification 层接线 | 构建类工具返回前**自验产物**；写文件工具回读校验 |
| **P7** | 工具失败错误分类 + 策略 | 每类错误有对应回喂策略，有回归用例 |
| **P8** | 本地引擎受约束解码（GBNF） | 工具轮 JSON 解析失败率显著下降 |

## 四、需要拍板的两个点

1. **P2 起必须有真机验证**：proot 里跑 Gradle 是重活（首次可能要十几分钟、
   吃 2–4GB 内存）。需要确认目标机型的内存/存储，以及**是否允许首次装配耗时很长**。
2. **P6–P8 与「闭环框架/长程编排永久关闭」的既有决定冲突**：
   `ClosedLoopExecutor` / `LongHorizonOrchestrator` 当年是你明令关闭并禁止 AI 主动启用的。
   现在你说「思考构架不完整」——**这两件事需要你明确：是维持关闭、还是解除禁令**。
   我倾向：**验证层（Verification）独立出来先做**（它不依赖那套编排，且直接解决"说做完了其实没做"），
   而 Planning/Reflection 是否恢复由你定。
