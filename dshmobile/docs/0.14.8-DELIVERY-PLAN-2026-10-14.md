## §0 一句话结论

**四项都成立，但你的排序里有一项排错了，另有一项的前提是坏的。**

- **门禁优化不是「第三项」，是当前最大且最确定的收益**：本轮实测 8 条读快照的门禁在**单 ABI** 下合计
  **228.1 s**，而它们只打印了 **9,191 字节**。参照系是整条本地链在发布 job 里跑 **1,047 s** ——
  这 8 条占了两成，且几乎全是重复解码同一份 160 MB 归档。
- **日志优化排最后是对的，但理由和你想的不同**：日志本身不是瓶颈（9,191 B / 228 s）。它的真实风险是
  **删日志会删掉证据**，而本项目的历史实锤（#352、#353、#359）全部靠日志与探针定位。所以这一项必须先
  定义「什么算信息不丢」的判据，再动手，否则是一次不可逆的取证能力削弱。
- **启动加速保留优先级，但前置条件未满足**：见 §2.1，尺子还没修好。
- **本地文件整理是最高性价比项，而且一半的答案已经在仓库里躺着没人用**：见 §2.2。

## §1 本轮实测（新数据，替换掉全部外推值）

### 1.1 快照解码的真实代价

样本：`.deploy-tmp/snapshot-013/x86_64/snapshot.tar.xz`，160,970,448 B，**49,030 条目**，完整解压后
**41,133 个文件 / 707,454,415 B**。

| 操作 | 实测 | 说明 |
|---|---:|---|
| `tar -tf`（列全部成员，系统 bsdtar） | **11.3 s** | 重复跑第二次 11.8 s，第三次 11.6 s —— **页缓存无效** |
| `tar -xO -f` 取**单个**成员 | **10.8 s** | xz 不可随机寻址，取一个成员 = 全量解码一遍 |
| `tar -xO -f` 取另一个成员 | 11.6 s | 同上，不因「上次解过」而变快 |
| 完整解压到磁盘 | **32.3 s** | 主要是 41k 次小文件写的代价 |
| WSL 侧 `tar -tJf` 读 `/mnt/d`（9p） | **26.4 s** | 比原生慢 2.3 倍 |
| WSL 侧先拷进 ext4 再列 | 17.4 s | 含拷贝，仍比 9p 快 |
| WSL `sha256sum` 纯 9p 读 | 2.9 s | 纯读带宽对照 |
| Windows `Get-FileHash` | 0.98 s | 同一份文件的宿主侧成本 |

**结论：`tar -tf` 与 `tar -xO <单个成员>` 等价昂贵。任何「每个成员调一次 tar -xO」的循环，
代价 = 成员数 × 11 s。**

### 1.3 三个归因（都有受控对照）

**A. `check-snapshot-secrets` 的 67.7 s 里，约 50 s 花在 WSL 往返上，不是花在判据上。**

它走 `lib/shell.mjs` 的 `sh()`，Windows 上展开为 `wsl.exe -e bash -lc ...`，于是在 WSL 里解压
`/mnt/d` 上的 160 MB 归档。对照：同一份文件 WSL **26.4 s** vs 原生 **11.3 s**。
扣掉解码本身，剩下约 40 s 是 `wsl.exe` 进程启动 + 9p 往返 + `bash -lc` 冷启动。
**这条门禁产出 56 字节，成本 67.7 秒。**

**B. 至少有两条门禁在循环里取成员，每次循环都是一次全量解码。**

- `check-runtime-assets.mjs:158` —— 在 `for (const asset of assets)` 里调用 `readFromSnapshot(target)`，
  而 `readFromSnapshot` 是 `execFileSync(TAR, ['-xO', '-f', SNAP, path])`。
  `assets/patched/` 实测有 3 个资产 ⇒ **3 次全量解码**。32.3 s ÷ 3 ≈ 10.8 s，与探针完全吻合。
- `check-perf-instrumentation.mjs:180→186,195` —— 同一模式：1 个引擎成员 + 2 个 profile 成员 = **3 次全量解码**，
  34.2 s ÷ 3 ≈ 11.4 s，同样吻合。

**这两处不是新问题，仓库里已经有成文的正确做法**：`check-mcp-client-deps.mjs:90-91` 写着
「为什么不用『每包一次 tar -xOf』：49k 成员的 tar 每个包一次 = 每次都要重扫索引，闭包十几个包就要几分钟
（本轮实测超时）。一次 `-xOf` 取回全部 package.json 只需一次扫描。」
它与 `check-inject-completeness.mjs:68-69`（「逐成员 tar -xO 会对 170MB xz 重解压 N 次，实测 >10min 超时」）
**是同一个教训的两次独立记录**。**新两处是同一形态的漏网。** 这意味着修复不是发明，是补齐已有范式。

**C. 你猜的「哈希对上就不用全量重解压」，落点是错的 —— 但直觉是对的。**

必须诚实说明三件事：

1. **当前门禁链里不存在任何基于内容哈希的短路。** 全仓搜索无命中。
2. **`snapshot.sha256` 是自证的**，不能当判据：它是 `build-apk-013.ps1` 自己写出来的声明值，
   `check-snapshot-fingerprint.mjs` 只断言 `sha256(tar) == 该文件`。`check-snapshot-decode.mjs` 的文件头
   已经把这件事写明了（「声明值与 tar 由同一条构建步骤产生」）。
3. **更关键：慢的那几条门禁根本不校验完整性，它们在读内容。** 一个哈希短路**既不会让它们变快**
   （哈希是 0.98 s，解码是 11.3 s，本来就是两个量级），**若用它跳过，就是直接删掉防线**。

   但你的直觉有一个**正确且可用的落点**：**把哈希当缓存键，而不是当跳过理由。**
   「tar 内容哈希未变 **且** 该门禁脚本自身哈希未变 ⇒ 它的判决不可能变」是一次**健全的记忆化**，
   与「跳过校验」是两件事。区别在于：判决被**复用**，而不是被**放弃**。设计约束见 §2.3 P5。

### 2.3 门禁优化 —— 同意，且是本轮第一优先

**目标口径（可验收）**：读快照的门禁在单 ABI 下的**冷跑**合计从 228.1 s 降到 60 s 以内，
且**判据强度不降**（每条门禁的负控仍然判红）。

**原子 PR 分解（每个都能独立 revert，每个都有自带的 before/after）**：

| 序 | PR | 触及文件 | 预期 | 判据强度 |
|---|---|---|---|---|
| **P1** | 逐门禁耗时记账 | `scripts/check-release-gates.mjs` | 0（可观测性） | 不变（只加打印与 JSON 产物） |
| **P2** | `check-snapshot-secrets` 原生解码，去掉 WSL 往返 | `scripts/check-snapshot-secrets.mjs` | 67.7 s → 约 11 s | 不变（同一 tar 成员集合） |
| **P3** | `check-runtime-assets` 批量取成员 | `scripts/check-runtime-assets.mjs` | 32.3 s → 约 12 s | 不变（比对的是同一批字节） |
| **P4** | `check-perf-instrumentation` 批量取成员 | `scripts/check-perf-instrumentation.mjs` | 34.2 s → 约 13 s | 不变 |
| ~~**P5**~~ | ~~判决记忆化（哈希键，见下）~~ | ~~`scripts/lib/tar-extract-cache.mjs` + 调用点~~ | **已裁定不做**：模块**退役删除**（2026-10-14；裁定依据与实测见本文 §2.2 的加粗段） | — |
| **P6** | 日志分层（见 2.4） | 多条 | 不确定 | **必须先定义判据** |

**P1 必须先合**。理由：现在全仓对门禁耗时的「事实」是 2026-09-26 的一次性测量（322.2 s / 411.5 s），
已经过期两个月，而且是在不同的机器负载与不同快照下测的。**没有持续的逐门禁计时，任何「优化后更快」
都只能靠一次性探针，无法回归。**

**P5 的设计约束（这是把你的直觉变成可靠工程的那一步）**：

- 缓存键必须**同时**包含 tar 内容哈希**与**该门禁脚本自身的内容哈希 —— 只键 tar 会在改判据后返回旧判决（假绿）；
- **严格档（`--require` / 发布链 / 发布前设备门禁）一律绕过缓存**，永远真跑；
- 缓存条目必须记录「何时、用哪个脚本哈希、对哪个 tar 哈希、判了什么」，可被审计；
- **必须自带反证**：构造一个「tar 未变、脚本已变」的输入，断言缓存未命中。
  没有这条反证，P5 就是一次把防线换成「看起来更快」的交易。

### 2.4 日志打印优化 —— 同意，但这一项最容易做坏

**实测事实**：8 条门禁 228 s 产出 **9,191 B**。门禁日志**不是**体积问题。
你要压的大概率是别的东西：引擎 `engine.log`、`boot-segments.log`、诊断包导出、logcat 采集、
以及构建链里那些被 `Select-Object -First N` 截断的原始输出。

**因此这一项的前置是「先量化，再删」，而不是「先删」**：

1. 先测四类日志的真实体积与增长速率（引擎日志、启动探针、诊断包、链上输出）；
2. 定义**信息不丢**的判据 —— 建议口径：**任何一次设备侧故障（boot-fail / ANR / 崩溃）仍然必须能从
   留存日志里唯一确定根因**。这条判据的可操作形式是：拿 0.14.7 已归档的四个真因
   （#352 首页取图早于 Loader 收敛、#353 client 行静默消失、#359 尾部校验、前台服务崩溃）当**回归样例**，
   改动后逐条复现定位路径。**复现不出来 = 信息丢了。**
3. 再分层：默认档精简，`--verbose` / 诊断模式保留全量；**禁止直接删除**任何被上述样例依赖的行。

**没有第 1、2 步就动手，等于把本项目的取证能力换成一点磁盘，不划算。**

## §3 协议：原子化交付（拟并入 AGENTS.md）

### 3.1 现状的两处冲突

你提的模型与现行铁律有两处直接冲突，必须显式改，不能并存：

1. **铁律 3「批量改、统一验」**：要求成组改动一次改完、一次验。与「原子 PR、可分段」冲突。
2. **铁律 2「模拟器优先 + 三层验收」**：要求 PR 之前完成三层验收。与「最后统一跑测试」冲突。

### 3.2 建议：拆开**归因**与**验证**，不要拆掉验证

你要的其实是**归因能力**：一个大 PR 失败时不知道是哪条改动干的。原子 PR 解决它。
但「最后统一跑测试」如果被理解成「每个 PR 不验」，`main` 会积累一串未验证改动，
到发版时变成一次性大爆炸调试 —— 那正是你抱怨的「卡很久」的更坏版本。

**建议条款（替换铁律 3，保留铁律 2）**：

- **原子 PR**：一个 PR = 一个逻辑改动，可独立 revert。禁止把「修 bug + 重构 + 顺手优化」混在一起。
- **每 PR 必须携带与其风险类相符的最廉价充分证据**：
  - **L0 文档/注释**：CI 绿即可；
  - **L1 门禁/脚本逻辑**：该门禁自身的 `--self-test` + **一条受控负控**（证明它仍会判红）；
  - **L2 安全敏感面**（快照事务 / 签名 / 门禁自身判据 / 桥协议）：**即时三层验收**，不延后；
  - **L3 UI / UX / 壳侧行为**：**模拟器三层验收**，不延后。
- **统一测试点前移到「发版计划确定时」**，内容是：双 ABI 全链、冷启动矩阵、真机补充门禁。
  它**替代不了**上面每档的证据，只做**集成**验证。
- **合并顺序**：L2 面先合、镜像面（铁律 6）先合 apk 侧。
