## 1. 各成员核心结论（每位 1 段，转述为主）

### 🔧 排障手（调试与根因）
- 核心判断：逐层排查确认 `parse()` 本来就会遍历 `tool_calls` 数组解析**多个**调用；`QuroToolEngine.execute()` 也是 `calls.map {…}` 顺序执行多个并返回**同序**结果列表——链路本身通。**真正的 bug 在 `QuroAssistant.ask()` 的循环**：`result.calls.map { c -> c.copy(id = callId) }` 把整轮所有 call 都复制成**同一个 `callId`**，随后所有工具结果也回指这个相同的 id。OpenAI 协议要求每个 `tool_call` 的 id 唯一、`tool` 结果消息的 `tool_call_id` 须回指原 call——id 撞车后下一条发给模型的消息是**畸形**的，模型无法正确区分「哪个结果对应哪个工具」，于是只能退化成一次一个。
- 关键建议：给每个 call 赋唯一 id（`call_<nano>_<round>_<idx>`），结果与 call 按下标配对回灌；同时将整轮执行异常从「一条错误」改为「每个 call 各一条错误」，保持 id 配对不丢。

### 🔍 产品官（编排策略）
- 核心判断：用户要的是「思考 → 批量调多个工具 → 汇总 → 回复」的**灵活组合**，而不是「思考 → 调一个 → 再思考 → 再一个」的死板串行。除代码 bug 外，小米 MiMo 这类小模型**默认倾向一次只吐一个 tool_call**——光修 id 不够，还得在系统提示词里**明确教模型批量发**。
- 关键建议：在共享的「平台 manifest」里加一节工具编排规则——相互独立的动作要在同一条回复里一次性发多个 `tool_calls`；只有强依赖（后一个参数来自前一个结果）才分批。该 manifest 聊天与语音球共用，一处改两入口生效。

## ⚠️ 待完善 / 已知局限

- 本轮修复让「模型想并发时」能正确并发；但**模型是否愿意并发**取决于模型本身。小米 MiMo 小模型实测常一次只吐一个 tool_call，仅靠 prompt 引导，不能 100% 保证批量。
- `execute()` 当前为**顺序**执行多个工具（一轮内仍一个接一个跑，但只占「一轮模型调用」而非「多轮」）。对绝大多数本地设备动作足够快；真正的并行加速为后续增强项（见行动项 3）。
- 语音球入口（`QuroVoiceBallService`）同样走 `QuroAssistant.ask()`，已随本次修复一并受益，无需单独改。
- 早前旧版本（修复前）写入磁盘的对话若含畸形工具消息，加载时可能出现历史脏数据；新会话正常。
